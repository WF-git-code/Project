## 1. 项目概述与架构

### 1.1 项目简介

这是一个基于 C++14 的高性能预约票务系统，实现了完整的用户注册登录、票务查询、在线预约等功能。系统采用当前互联网企业主流的 Reactor 模式构建，结合线程池实现高并发处理能力，同时引入 Redis 作为缓存层和分布式锁组件，配合 MySQL 实现数据持久化。

系统架构包含以下核心组件：

- **Epoll事件循环**：主线程负责监听客户端连接
- **CachedThreadPool**：缓存式线程池，核心线程常驻，非核心线程动态伸缩
- **MySQL连接池**：数据库连接池，采用LRU策略优化连接复用
- **Redis连接池**：缓存和分布式锁，支持票务信息缓存
- **异步日志系统**：双缓冲机制，后台线程批量写盘

### 1.2 技术栈

### 1.3 核心设计模式

**1. Reactor模式（网络层）**

主线程负责Epoll多路复用，Worker线程池处理业务逻辑。特点：单线程监听，多线程并发处理。

**2. 生产者-消费者模式（线程池）**

Epoll线程作为生产者放入任务队列，Worker线程作为消费者从队列取任务执行。特点：解耦IO线程和业务线程。

**3. RAII模式（资源管理）**

ConnectionGuard自动获取和归还数据库连接。特点：构造函数获取，析构函数释放。

**4. 单例模式（全局资源）**

MySQL连接池、Redis连接池、LoggerManager都采用单例模式。

### 1.4 核心技术亮点

- **Epoll + EPOLLONESHOT**：高效I/O多路复用，保证线程安全
- **缓存式线程池**：核心线程常驻，非核心线程动态扩容回收
- **MySQL连接池**：复用连接，减少握手开销，数据库操作性能提升10倍+
- **Redis连接池**：复用Redis连接，缓存命中率提升，锁竞争降低
- **票务信息缓存**：Redis缓存ticket:list，TTL=300秒
- **分布式锁**：SET NX PX实现，防止超卖
- **缓存一致性**：先更新数据库再删缓存
- **双缓冲异步日志**：前台线程写内存，后台线程写磁盘
- **事务 + 乐观锁**：保证数据一致性，防止超卖
- **RAII智能管理**：Socket/Connection自动释放

```cpp
    FILE *fp = fopen(filename.c_str(), "r");

        return false;
```

```cpp
    char buff[256] = {0};
```

## 3. 逐代码学习 - 自定义TCP协议

### 3.1 为什么需要自定义协议？

**问题场景**：

- TCP是字节流协议，没有消息边界
- 多个小数据包可能被合并发送（粘包）
- 一个大数据包可能被拆分发送（拆包）

**解决方案**：自定义协议，添加消息边界标识。

```
┌─────────────────────────────────────────────────────────────┐
│  TCP粘包拆包问题示意                                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  客户端发送:  [数据包1] [数据包2] [数据包3]                   │
│                                                             │
│  服务器收到的可能情况:                                       │
│  ├─ 情况1 (正常):     [数据包1][数据包2][数据包3]            │
│  ├─ 情况2 (粘包):     [数据包1+数据包2] [数据包3]           │
│  ├─ 情况3 (拆包):     [数据包1前半] [数据包1后半+数据包2]    │
│  └─ 情况4 (混合):     [数据包1+数据包2前半] [数据包2后半]    │
│                                                             │
│  解决方案: 自定义协议 = 魔数 + 长度 + 命令 + 数据             │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 协议头结构体（内存对齐问题）

```cpp
// 协议魔数，用于标识有效数据包
constexpr uint32_t PROTOCOL_MAGIC = 0xCAFEBABE;

// 协议头结构（使用1字节对齐，避免内存对齐问题）
#pragma pack(push, 1)
struct ProtocolHeader {
    uint32_t magic;     // 魔数 0xCAFEBABE (网络字节序)
    uint32_t length;    // 数据长度（不包含协议头, 网络字节序）
    uint8_t command;    // 命令类型
};
#pragma pack(pop)

// 协议头大小（固定9字节）
constexpr size_t PROTOCOL_HEADER_SIZE = 9;
```

**为什么要用** **`#pragma pack`？**

> 默认情况下，编译器会对结构体进行内存对齐（通常4字节或8字节对齐），这会导致 ProtocolHeader 的大小变成12字节而不是9字节。使用 `#pragma pack(push, 1)` 强制1字节对齐，确保协议头正好是9字节。

**字节序说明**：

- 网络传输使用大端序（Big Endian）
- 使用 `htonl()` 转换为主机序到网络序
- 使用 `ntohl()` 转换为网络序到主机序

### 3.5 打包发送（pack）

```cpp
// 封装协议数据
static std::string pack(uint8_t command, const std::string& data) {
    std::string result;
    
    // 构建协议头
    ProtocolHeader header;
    header.magic = htonl(PROTOCOL_MAGIC);  // 魔数转网络字节序
    header.length = htonl(static_cast<uint32_t>(data.size()));  // 长度转网络字节序
    header.command = command;
    
    // 添加协议头（9字节）
    result.append(reinterpret_cast<const char*>(&header), PROTOCOL_HEADER_SIZE);
    // 添加数据部分
    result.append(data);
    
    return result;
}
```

**关键要点**：

1. 使用标准的 `htonl()` 函数进行字节序转换（包含在 `<arpa/inet.h>` 中）
2. 魔数和长度都需要转换，命令字节不需要（单字节无字节序问题）
3. 使用 `reinterpret_cast` 直接将结构体转为字节流

### 3.6 接收与解析流程（receive\_and\_parse）

```cpp
// 接收数据并解析
bool receive_and_parse(const char* data, size_t len, 
                       std::string& output_data, uint8_t& output_cmd) {
    // 将新数据追加到缓冲区（如果有的话）
    if (data != nullptr && len > 0) {
        buffer_.insert(buffer_.end(), data, data + len);
    }
    
    // 循环尝试解析数据包（可能一次收到多个）
    while (buffer_.size() >= PROTOCOL_HEADER_SIZE) {
        // 读取协议头
        ProtocolHeader* header = reinterpret_cast<ProtocolHeader*>(buffer_.data());
        
        // 检查魔数是否正确 (网络字节序转主机字节序再比较)
        uint32_t magic_host = ntohl(header->magic);
        if (magic_host != PROTOCOL_MAGIC) {
            // 魔数不匹配，丢弃一个字节继续找
            buffer_.erase(buffer_.begin());
            continue;
        }
        
        // 获取数据长度（网络字节序转主机字节序）
        uint32_t data_len = ntohl(header->length);
        
        // 计算完整数据包大小
        size_t packet_size = PROTOCOL_HEADER_SIZE + data_len;
        
        // 检查是否有完整的数据
        if (buffer_.size() < packet_size) {
            // 数据不完整，等待更多数据
            break;
        }
        
        // 提取业务数据
        output_cmd = header->command;
        output_data.assign(buffer_.data() + PROTOCOL_HEADER_SIZE, data_len);
        
        // 从缓冲区移除已处理的数据
        buffer_.erase(buffer_.begin(), buffer_.begin() + packet_size);
        
        return true;  // 成功解析一个数据包
    }
    
    return false;  // 没有完整数据包
}
```

### 3.8 面试问答

> **Q**: 为什么要用魔数？
> **A**: 快速识别协议有效性，防止垃圾数据干扰。魔数不匹配时可以逐步丢弃字节继续查找。

> **Q**: 为什么长度要用大端序？
> **A**: 网络传输约定，保证跨平台兼容性。不同CPU架构（x86小端序 vs ARM大端序）能正确解析。

> **Q**: 拆包了怎么办？
> **A**: 用缓冲区暂存不完整数据，等下次数据到达后再解析。这是处理粘包拆包的核心思路。

> **Q**: 为什么要用 `#pragma pack`？
> **A**: 强制1字节对齐，确保协议头正好是9字节，避免编译器自动对齐导致协议解析错误。

> **Q**: 如何处理无效数据？
> **A**: 魔数不匹配时，逐字节丢弃并继续查找有效数据包，不会因为一个错误包影响后续数据。

> **Q**: 缓冲区预分配4KB的原因？
> **A**: 平衡内存占用和分配频率，4KB是网络数据包的常见大小，能减少内存分配次数。

```cpp
        return false;
```

```cpp
void ListenSocket::Handle_Data()
{
    // 1. accept() 新连接
    struct sockaddr_in client_addr;
    socklen_t client_addr_len = sizeof(client_addr);
    
    int client_fd = accept(m_fd, (struct sockaddr*)&client_addr, &client_addr_len);
    if (client_fd < 0) {
        ResetEvent();
        return;
    }
    
    LOG_INFO << "[Server] 新连接: " << inet_ntoa(client_addr.sin_addr)
             << ":" << ntohs(client_addr.sin_port);
    
    // 2. 设置非阻塞（ET模式要求非阻塞）
    int flags = fcntl(client_fd, F_GETFL, 0);
    fcntl(client_fd, F_SETFL, flags | O_NONBLOCK);
    
    // 3. 创建 ConnectSocket 并注册到 Epoll
    ConnectSocket* conn_sock = new ConnectSocket(client_fd, m_epfd);
    struct epoll_event ev;
    ev.data.ptr = conn_sock;
    ev.events = EPOLLIN | EPOLLONESHOT | EPOLLET;
    epoll_ctl(m_epfd, EPOLL_CTL_ADD, client_fd, &ev);
    
    // 4. 重置监听Socket的事件
    ResetEvent();
}
```

```cpp
{

    char buff[4096] = {0};
    int len = recv(m_fd, buff, sizeof(buff) - 1, 0);
    
    // 客户端断开连接

        ResetEvent();
        return;

    // 3. 提取操作类型

    extern CachedThreadPool* g_thread_pool;
    g_thread_pool->Excute([this]() {
        // Worker线程中执行的代码
        switch (m_op_type) {
            case REGISTER:   User_Register(); break;
            case LOGIN:      User_Login(); break;
            case SHOW_TICKET: Show_Ticket(); break;
            case BOOK_TICKET: Yd_Ticket(); break;
            case MY_BOOKINGS: Show_My_Yuyue(); break;
            case CANCEL_BOOKING: Cancel_Yuyue(); break;
            default: Send_ERR(); break;
```

```cpp
template<class Func, class...Args>
auto Submit(Func&& func, Args&&...args) {
    // 1. 完美转发，用 packaged_task 包装
    using RetType = decltype(func(args...));
    auto task = std::make_shared<std::packaged_task<RetType()>>(
        std::bind(std::forward<Func>(func), std::forward<Args>(args)...)
    );
    std::future<RetType> result = task->get_future();
    
    // 2. 任务入队
    if (TaskList.Put([task]() { (*task)(); }) != 0) {
        // 队列满了，由提交线程直接执行（降级策略）
        (*task)();
    }
    
    // 3. 尝试添加新线程
    AddNewThread();
    
    return result;
}
```

```cpp
void Running_Thread() {
    auto Tid = std::this_thread::get_id();
    auto StartTime = std::chrono::high_resolution_clock::now();
    
    // 检查是否是非核心线程
    auto id = Diltation_Thread_Pool.find(Tid);
    
    while (Running) {
        Task task;
        
        // 非核心线程的超时回收逻辑
        if (id != Diltation_Thread_Pool.end()) {
            if (TaskList.size() == 0) {
                auto now = std::chrono::high_resolution_clock::now();
                auto IntervalTime = std::chrono::duration_cast<std::chrono::seconds>(
                    now - StartTime
                ).count();
                
                std::unique_lock<std::mutex> locker(Mutex);
                // 空闲超时且不是空池
                if (IntervalTime >= Thread_Wait_Time && !Diltation_Thread_Pool.empty()) {
                    id->second->detach();  // 分离线程
                    Diltation_Thread_Pool.erase(id);
                    --All_ThreadSize;
                    --Free_ThreadSize;
                    Thread_Exit.notify_all();
                    return;  // 线程退出
                }
            }
        }
        
        // 执行任务
        if (0 == TaskList.Take(task)) {  // 取任务成功
            if (task && Running) {
                --Free_ThreadSize;    // 忙
                task();               // 执行
                ++Free_ThreadSize;    // 又空闲了
                
                // 非核心线程，重置空闲时间
                if (id != Diltation_Thread_Pool.end()) {
                    StartTime = std::chrono::high_resolution_clock::now();
                }
            }
        }
    }
}
```

### 6.2 LRU算法优化

**为什么需要LRU**：

- MySQL连接长时间不使用会被服务器断开
- LRU优先复用最近使用的连接，减少连接失效概率
- 自动清理无效连接，保证连接池健康

```
LRU连接池工作原理：
┌─────────────────────────────────────────────────────────────┐
│ 连接链表（最近使用的在头部）                                   │
│  ┌──────┬──────┬──────┬──────┬──────┐                      │
│  │ conn1│ conn2│ conn3│ conn4│ conn5│                      │
│  │(最近) │      │      │      │(最远)│                      │
│  └──────┴──────┴──────┴──────┴──────┘                      │
│                                                            │
│ 获取连接：取头部连接，使用后归还到头部                        │
│ 归还连接：放到头部，标记为最近使用                           │
│ 清理策略：获取时检查连接有效性，无效则丢弃并补充              │
└─────────────────────────────────────────────────────────────┘
```

### 6.3 核心实现

```cpp
class MysqlConnection {
public:
    // 检查连接是否有效（使用mysql_ping）
    bool valid() {
        return mysql_ping(conn_) == 0;
    }
    
    // 更新最后使用时间
    void update_last_used() {
        last_used_ = std::chrono::steady_clock::now();
    }
    
private:
    MYSQL* conn_;
    bool in_use_;
    std::chrono::steady_clock::time_point last_used_;  // LRU时间戳
};

class MysqlConnectionPool {
public:
    // 单例模式（Meyers单例，线程安全）
    static MysqlConnectionPool& getInstance() {
        static MysqlConnectionPool instance;
        return instance;
    }
    
    // 获取连接（LRU优化）
    std::shared_ptr<MysqlConnection> getConnection() {
        std::unique_lock<std::mutex> lock(mutex_);
        
        // 等待有空闲连接
        cond_.wait(lock, [this] {
            return !connections_.empty() || !running_;
        });
        
        if (!running_) return nullptr;
        
        // LRU策略：从链表头部获取最近使用的连接
        // 同时检查连接有效性，无效则跳过
        for (auto it = connections_.begin(); it != connections_.end(); ) {
            if ((*it)->valid()) {
                auto conn = *it;
                connections_.erase(it);  // 从链表移除
                conn->set_in_use(true);
                return conn;
            } else {
                // 连接失效，清理并补充新连接
                it = connections_.erase(it);
                addNewConnection();
            }
        }
        
        // 如果所有连接都失效，补充一个新连接
        return createAndAddConnection();
    }
    
    // 归还连接（LRU优化）
    void returnConnection(std::shared_ptr<MysqlConnection> conn) {
        if (!conn) return;
        
        std::lock_guard<std::mutex> lock(mutex_);
        
        // LRU策略：归还时放到链表头部（标记为最近使用）
        conn->set_in_use(false);
        conn->update_last_used();
        
        // 检查连接是否仍然有效
        if (conn->valid()) {
            connections_.push_front(conn);  // LRU：放到头部
        } else {
            // 连接失效，补充新连接
            addNewConnection();
        }
        
        cond_.notify_one();
    }
    
private:
    std::list<std::shared_ptr<MysqlConnection>> connections_;  // LRU链表
    std::mutex mutex_;
    std::condition_variable cond_;
};
```

### 7.4 RedisConnectionPool类 - 连接池核心（LRU优化）

看 [RedisConnectionPool.hpp#L33-L125](file:///home/wf/linux_new_project/server/RedisConnectionPool.hpp#L33-L125)

```cpp
class RedisConnectionPool {
public:
    // 单例模式（Meyers单例，C++11保证线程安全）
    static RedisConnectionPool& getInstance() {
        static RedisConnectionPool instance;
        return instance;
    }

    // 初始化连接池
    void init(const std::string& host, int port, 
              const std::string& password = "", int pool_size = 4) {
        std::lock_guard<std::mutex> lock(mutex_);
        
        host_ = host;
        port_ = port;
        password_ = password;
        pool_size_ = pool_size;
        running_ = true;

        // 预创建连接，加入list
        for (int i = 0; i < pool_size; ++i) {
            auto conn = createConnection();
            if (conn && conn->valid()) {
                connections_.push_back(std::move(conn));
            }
        }
    }

    // 获取连接（LRU优化：优先返回最近使用过的）
    std::shared_ptr<RedisConnection> getConnection() {
        std::unique_lock<std::mutex> lock(mutex_);
        
        // 条件变量等待
        cond_.wait(lock, [this] {
            // 检查list中是否有空闲连接
            for (auto& conn : connections_) {
                if (!conn->in_use()) return true;
            }
            return !running_;
        });

        if (!running_) return nullptr;

        // LRU算法：先清理无效连接，再找有效连接
        cleanupInvalidConnections();
        
        // 遍历找到第一个空闲且有效的连接
        for (auto it = connections_.begin(); it != connections_.end(); ++it) {
            if (!(*it)->in_use() && (*it)->valid()) {
                auto conn = *it;
                
                // LRU策略：把取出来的连接从原位置删除，移到list头部
                connections_.erase(it);
                connections_.push_front(conn);
                
                conn->set_in_use(true);
                conn->update_last_used();  // 更新最后使用时间
                return conn;
            }
        }
        
        return nullptr;
    }

    // 归还连接（LRU优化：放到list头部）
    void returnConnection(std::shared_ptr<RedisConnection> conn) {
        if (!conn) return;

        std::lock_guard<std::mutex> lock(mutex_);
        
        // 连接有效性检查：无效连接不归还，直接丢弃
        if (!conn->valid()) {
            std::cerr << "Redis连接已失效，丢弃" << std::endl;
            // 尝试创建新连接补充
            auto new_conn = createConnection();
            if (new_conn && new_conn->valid()) {
                connections_.push_back(std::move(new_conn));
            }
            cond_.notify_one();
            return;
        }
        
        conn->set_in_use(false);
        conn->update_last_used();  // 更新最后使用时间
        
        // LRU策略：归还的连接放到list头部（标记为最近使用）
        connections_.push_front(conn);
        
        cond_.notify_one();
    }

private:
    // 清理无效连接（LRU辅助）
    void cleanupInvalidConnections() {
        auto it = connections_.begin();
        while (it != connections_.end()) {
            if (!(*it)->valid() && !(*it)->in_use()) {
                std::cerr << "清理无效Redis连接" << std::endl;
                it = connections_.erase(it);
            } else {
                ++it;
            }
        }
    }

    // 使用list替代queue，便于LRU管理
    std::list<std::shared_ptr<RedisConnection>> connections_;
    std::mutex mutex_;
    std::condition_variable cond_;
    std::string host_;
    int port_;
    std::string password_;
    int pool_size_;
    bool running_;
};
```

### 7.6 连接池设计要点（面试必问）

**Q: 为什么用list而不是queue？**

```
用list的原因（LRU优化）：
┌─────────────────────────────────────────────────────────────────────┐
│ 1. 支持头部插入：归还连接放到头部，标记为最近使用                    │
│ 2. 支持任意位置删除：获取连接时从头部取                             │
│ 3. LRU算法实现：最近使用的在头部，最久未用的在尾部                  │
│                                                                    │
│ 用queue的问题：                                                    │
│ - 只能从尾部取，无法实现LRU                                        │
│ - 无法将连接移到头部                                               │
│ - 无法按使用时间排序                                               │
└─────────────────────────────────────────────────────────────────────┘
```

**Q: 为什么用shared\_ptr？**

```
shared_ptr的原因：
┌─────────────────────────────────────────────────────────────────────┐
│ 1. 自动管理生命周期：引用计数为0时自动析构                          │
│ 2. 线程安全：引用计数的增减是原子操作                               │
│ 3. 防止误释放：Guard持有期间，连接不会被其他线程拿走                │
│                                                                    │
│ 注意：shared_ptr本身线程安全，但Redis连接操作需要外部同步！         │
│       这里的设计是：每个连接同一时间只被一个线程使用                │
└─────────────────────────────────────────────────────────────────────┘
```

### 8.3 分布式锁实现

```cpp
// 生成唯一锁值（线程ID + 时间戳 + 序列号）
std::string Generate_Lock_Value()
{
    static std::atomic<uint64_t> counter(0);
    uint64_t timestamp = std::chrono::system_clock::now().time_since_epoch().count();
    uint64_t tid = std::hash<std::thread::id>()(std::this_thread::get_id());
    uint64_t seq = counter.fetch_add(1);
    return std::to_string(timestamp) + "_" + std::to_string(tid) + "_" + std::to_string(seq);
}

// 获取Redis分布式锁（带唯一ID）
// 返回值：锁的唯一值，用于解锁时验证
std::string Redis_Lock(const std::string &key, int timeout_ms)
{
    redis_pool::RedisConnectionGuard guard;
    if (!guard.valid()) {
        return "";
    }

    // 生成唯一锁值
    std::string lock_value = Generate_Lock_Value();
    
    // SET key value NX PX timeout_ms
    // NX: 只有key不存在时才设置（Not eXists）
    // PX: 设置毫秒级过期时间
    redisReply* reply = (redisReply*)redisCommand(guard.get(), "SET %s %s NX PX %d", 
                                                   key.c_str(), lock_value.c_str(), timeout_ms);
    
    bool success = reply && reply->type == REDIS_REPLY_STATUS && strcmp(reply->str, "OK") == 0;
    if (reply) freeReplyObject(reply);
    
    if (success) {
        LOG_DEBUG << "[Redis] 获取锁成功: " << key << ", value: " << lock_value;
        return lock_value;
    } else {
        LOG_DEBUG << "[Redis] 获取锁失败: " << key;
        return "";
    }
}

// 释放Redis分布式锁（使用Lua脚本保证原子性）
bool Redis_Unlock(const std::string &key, const std::string &lock_value)
{
    redis_pool::RedisConnectionGuard guard;
    if (!guard.valid()) {
        return false;
    }

    // Lua脚本：只有当锁的值匹配时才删除，避免误删
    // KEYS[1]: 锁的key
    // ARGV[1]: 锁的唯一值
    const char* lua_script = 
        "if redis.call('GET', KEYS[1]) == ARGV[1] then "
        "    return redis.call('DEL', KEYS[1]) "
        "else "
        "    return 0 "
        "end";

    redisReply* reply = (redisReply*)redisCommand(guard.get(), 
                                                   "EVAL %s 1 %s %s", 
                                                   lua_script, 
                                                   key.c_str(), 
                                                   lock_value.c_str());
    
    bool success = reply && reply->type == REDIS_REPLY_INTEGER && reply->integer == 1;
    if (reply) freeReplyObject(reply);
    
    if (success) {
        LOG_DEBUG << "[Redis] 释放锁成功: " << key << ", value: " << lock_value;
    } else {
        LOG_WARN << "[Redis] 释放锁失败(可能已过期或被其他线程持有): " << key;
    }
    
    return success;
}
```

**改进说明**：
1. **唯一锁值**：使用时间戳+线程ID+序列号生成唯一值，避免误删别人的锁
2. **Lua脚本原子性**：GET和DEL在一个Lua脚本中执行，避免竞态条件
3. **谁加锁谁解锁**：只有持有正确锁值的线程才能释放锁

```cpp
    mysql_query(conn, "COMMIT");

    // Step 3: 预约成功，清除缓存
    // 为什么删缓存而不是更新缓存？
    // - 删缓存更简单，下次查询时自动从DB加载最新数据
    // - 避免缓存和DB不一致的问题
    Cache_Delete_Ticket_List();
    LOG_INFO << "[Redis] 缓存已清除: ticket:list";

    // Step 4: 释放分布式锁
    Redis_Unlock(lock_key);
    LOG_INFO << "[Redis] 锁已释放: " << lock_key;

    return true;
}
```

### 8.5 缓存一致性策略（面试重点）

**为什么用"先更新数据库，再删缓存"？**

```
┌─────────────────────────────────────────────────────────────────────┐
│                  三种缓存一致性策略对比                              │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│ 1. 先更新缓存，再更新数据库                                         │
│    问题：如果缓存更新成功，数据库更新失败                       │
│    结果：缓存是新数据，数据库是旧数据 → 不一致！               │
│    结论：❌ 不可用                                              │
│                                                                     │
│ 2. 先删除缓存，再更新数据库                                         │
│    问题：删除缓存后，更新数据库前，有请求来了                   │
│          请求查数据库（旧数据）→ 写入缓存                       │
│          数据库更新完成（新数据）                               │
│    结果：缓存是旧数据，数据库是新数据 → 不一致！               │
│    结论：⚠️ 有问题，但可以用延迟双删解决                        │
│                                                                     │
│ 3. 先更新数据库，再删除缓存 ← 本项目采用                            │
│    分析：                                                        │
│      - 更新数据库成功，删除缓存失败：下次查询会加载新数据       │
│      - 更新数据库失败：缓存不删，数据一致                       │
│    优点：最安全，不一致概率最低                                  │
│    缺点：下次查询会穿透到数据库（但只有一次）                   │
│    结论：✅ 推荐                                                 │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 8.7 分布式锁的注意事项（面试重点）

**Q: 为什么设置过期时间？**

```
┌─────────────────────────────────────────────────────────────────────┐
│ 必须设置过期时间！                                                  │
│                                                                     │
│ 场景：获取锁后，程序crash了，锁没释放                               │
│ 结果：锁永远存在，其他线程永远拿不到锁                              │
│                                                                     │
│ 解决：设置过期时间，即使程序crash，锁也会自动释放                   │
│       本项目设置5秒超时                                             │
│                                                                     │
│ 注意：过期时间要合理                                                │
│ - 太短：业务还没执行完，锁就过期了，可能超卖                        │
│ - 太长：程序crash后，要等很久锁才释放                               │
│ - 建议：略大于业务执行时间                                          │
└─────────────────────────────────────────────────────────────────────┘
```

**Q: 这个分布式锁有什么问题？**

```
┌─────────────────────────────────────────────────────────────────────┐
│ 当前实现的潜在问题（面试可以讲，展示深度思考）                       │
│                                                                     │
│ 问题1：锁误删                                                       │
│ 场景：                                                        │
│   T1: 线程A获取锁，设置5秒过期                               │
│   T2: 线程A执行业务，但网络慢，执行了6秒                     │
│   T3: 锁过期自动释放                                         │
│   T4: 线程B获取锁                                            │
│   T5: 线程A执行完，DEL释放锁 → 把B的锁删了！                 │
│                                                              │
│ 解决：释放锁时检查value是否是自己设置的                      │
│       SET lock:ticket:1 threadA_uuid NX PX 5000             │
│       DEL前先GET，确认value==threadA_uuid才DEL               │
│       用Lua脚本保证原子性                                    │
│                                                                     │
│ 问题2：Redis主从切换                                                │
│ 场景：                                                        │
│   T1: 线程A在Master获取锁                                    │
│   T2: Master还没同步给Slave就crash                          │
│   T3: Slave升级为Master                                      │
│   T4: 线程B在新Master获取锁 → 成功！                         │
│   结果：两个线程同时持有锁                                    │
│                                                              │
│ 解决：RedLock算法（Redis官方推荐）                           │
│       同时在多个Redis实例获取锁，大多数成功才算成功           │
│                                                                     │
│ 结论：当前实现适合单机Redis，生产环境建议用RedLock                  │
└─────────────────────────────────────────────────────────────────────┘
```

### 8.9 为什么要设置过期时间TTL？（面试深度问题）

**设置TTL的5个原因**：

1. **防止内存无限增长**
   ```
   如果缓存永不过期，数据会一直积累
   → 内存耗尽
   → Redis崩溃
   → 系统不可用
   ```
2. **保证数据最终一致性**
   ```
   数据库数据变了，但缓存没变
   → 数据不一致
   → 设置TTL，缓存过期后自动从DB加载最新数据
   ```
3. **节省内存空间**
   ```
   内存是有限的资源
   → 热点数据放缓存
   → 冷数据自动过期清除
   → 内存利用率最大化
   ```
4. **防止缓存雪崩**
   ```
   所有缓存同时过期
   → 大量请求同时穿透到数据库
   → 数据库压力爆炸

   设置随机TTL：
   → 缓存过期时间分散
   → 请求分散到不同时刻
   → 数据库压力平滑
   ```
5. **业务容错**
   ```
   程序bug导致数据写入错误
   → 错误数据被缓存
   → 永不过期，永远错误

   设置TTL：
   → 错误数据最多存在TTL时间
   → 修复bug后，TTL过期自动恢复
   ```

**本项目TTL设置策略**：

| 缓存类型          | TTL    | 理由                 |
| ------------- | ------ | ------------------ |
| `ticket:list` | 300秒   | 票务数据变化不频繁，5分钟内基本一致 |
| `lock:*`      | 5000毫秒 | 锁的TTL由业务时间决定，5秒足够  |

**TTL设置的经验法则**：

```
TTL = 业务容忍的数据延迟时间

例如：
- 票务信息：5分钟够用（300秒）
- 秒杀商品：1-2秒（实时性要求高）
- 用户个人信息：30分钟（变化少）
- 验证码：5分钟（一次性）
```

```cpp
// 文件块上传
void ConnectSocket::File_Chunk()
{
    if (m_file_fd < 0) {
        LOG_ERROR << "文件未打开";
        Send_ERR();
        return;
    }

    // data字段包含文件数据
    std::string file_data = m_request["data"].asString();
    size_t chunk_offset = m_request["offset"].asUInt64();

    // 验证偏移
    if (chunk_offset != m_file_offset) {
        LOG_ERROR << "偏移不匹配: " << chunk_offset << " != " << m_file_offset;
        Send_ERR();
        return;
    }

    // 写入文件
    ssize_t bytes_written = write(m_file_fd, file_data.c_str(), file_data.size());
    if (bytes_written < 0) {
        LOG_ERROR << "写入文件失败";
        Send_ERR();
        return;
    }

    m_file_offset += bytes_written;

    LOG_DEBUG << "[FILE] 写入块: " << bytes_written << " bytes, 偏移: " << m_file_offset;

    Json::Value res;
    res["status"] = "OK";
    res["offset"] = (Json::UInt64)m_file_offset;
    Send_Jsonobj(res);
}
```

```cpp
{
```

```cpp
    cout << "+----------------------------------------+" << endl;
    cout << "|          文件上传                      |" << endl;
    cout << "+----------------------------------------+" << endl;
    cout << "|  请输入文件路径: ";

    cin.ignore();  // 忽略前面的换行

    size_t file_size = get_file_size(filepath);
    if (file_size == 0) {

        cout << "+----------------------------------------+" << endl;
        return;
    }

    string filename = get_file_basename(filepath);
    cout << "| 文件名: " << filename << endl;
    cout << "| 文件大小: " << file_size << " 字节" << endl;

    // 步骤1：检查断点
    Json::Value check_req;
    check_req["file_name"] = filename;
    Json::Value check_res;
    if (!Send_Request(CMD_FILE_CHECK, check_req, check_res)) {
        cout << "| 检查断点失败" << endl;
        cout << "+----------------------------------------+" << endl;
        return;
    }

    size_t offset = 0;
    bool file_exists = check_res["exists"].asBool();
    if (file_exists) {
        offset = check_res["offset"].asUInt64();
        cout << "| 发现断点，从偏移 " << offset << " 继续上传" << endl;
    } else {
        cout << "| 新文件，从开头开始上传" << endl;
    }

    // 步骤2：开始上传
    Json::Value start_req;
    start_req["file_name"] = filename;
    start_req["file_size"] = (Json::UInt64)file_size;
    Json::Value start_res;
    if (!Send_Request(CMD_FILE_START, start_req, start_res)) {
        cout << "| 开始上传失败" << endl;
        cout << "+----------------------------------------+" << endl;
        return;
    }

    if (start_res["status"].asString() != "OK") {
        cout << "| 开始上传失败" << endl;
        cout << "+----------------------------------------+" << endl;
        return;
    }

    // 再次确认offset（服务器可能有不同的偏移）
    offset = start_res["offset"].asUInt64();

    // 打开文件
    int fd = open(filepath.c_str(), O_RDONLY);
    if (fd < 0) {
        cout << "| 无法打开文件" << endl;
        cout << "+----------------------------------------+" << endl;
        return;
    }

    // 移动到指定偏移
    if (offset > 0) {
        lseek(fd, offset, SEEK_SET);
    }

    // 步骤3：分块上传
    const size_t CHUNK_SIZE = 8192;  // 每块8KB
    char chunk[CHUNK_SIZE];
    bool success = true;
    size_t total_sent = offset;

    cout << "| 上传进度: ";
    cout.flush();

    while (offset < file_size) {
        // 读取文件块
        ssize_t read_size = read(fd, chunk, CHUNK_SIZE);
        if (read_size <= 0) break;

        // 构造请求
        Json::Value chunk_req;
        chunk_req["offset"] = (Json::UInt64)offset;
        chunk_req["data"] = string(chunk, read_size);

        Json::Value chunk_res;
        if (!Send_Request(CMD_FILE_CHUNK, chunk_req, chunk_res)) {
            success = false;
            break;
        }

        if (chunk_res["status"].asString() != "OK") {
            success = false;
            break;
        }

        offset += read_size;
        total_sent += read_size;

        // 显示进度
        int percent = (int)((offset * 100) / file_size);
        cout << "\r| 上传进度: " << percent << "%";
        cout.flush();
    }

    cout << endl;
    close(fd);

    if (!success) {
        cout << "| 上传过程中失败" << endl;
        cout << "+----------------------------------------+" << endl;
        return;
    }

    // 步骤4：结束上传
    Json::Value end_req;  // 空请求
    Json::Value end_res;
    if (!Send_Request(CMD_FILE_END, end_req, end_res)) {
        cout << "| 结束上传失败" << endl;
        cout << "+----------------------------------------+" << endl;
        return;
    }

    if (end_res["status"].asString() != "OK") {
        cout << "| 上传失败" << endl;
        cout << "+----------------------------------------+" << endl;
        return;
    }

    cout << "+----------------------------------------+" << endl;
    cout << "|          上传成功!                     |" << endl;
    cout << "| 文件: " << end_res["file_name"].asString() << endl;
    cout << "| 大小: " << end_res["file_size"].asUInt64() << " 字节" << endl;
    cout << "+----------------------------------------+" << endl;
}
```

### 9.11 面试问答 - 大文件传输与断点续传

> **Q: 为什么选择8KB作为块大小？**
> **A:**
>
> - 8KB是TCP数据包的常见大小
> - 平衡了网络传输效率和内存占用
> - 太小会增加协议开销，太大容易受网络波动影响
>
> **Q: 如何防止重复上传同一文件？**
> **A:**
>
> - 先检查服务器是否已存在该文件
> - 从已存在文件的大小处继续上传
> - 文件上传完成后可以校验MD5确保完整性
>
> **Q: 网络中断后如何恢复？**
> **A:**
>
> - 客户端重新连接
> - 发送CMD\_FILE\_CHECK查询断点
> - 从断点处继续传输
> - 无需重新上传已传输部分
>
> **Q: 如何确保文件传输完整性？**
> **A:**
>
> - 方案1: 传输前计算文件MD5，传输后校验
> - 方案2: 每个文件块带校验和
> - 方案3: 传输完成后对比文件大小
>
> **Q: 同时上传多个文件如何处理？**
> **A:**
>
> - 每个连接独立维护文件状态（m\_file\_fd, m\_file\_offset）
> - 不同连接互不干扰
> - 通过多线程/多连接可并发上传

### 10.2 预约票务 - 事务 + 乐观锁 + Redis分布式锁（核心中的核心）

```cpp
bool MysqlClient::Db_Yd_Ticket(string& usertel, string& ticketid)
{
    // 1. 获取连接
    mysql_pool::ConnectionGuard guard;
    if (!guard.valid()) {
        LOG_ERROR << "获取数据库连接失败";
        return false;
    }
    
    MYSQL* conn = guard.get();
    
    // 2. 开启事务（BEGIN）
    mysql_query(conn, "BEGIN");
    
    char escaped_tel[512] = {0};
    mysql_real_escape_string(conn, escaped_tel, usertel.c_str(), usertel.length());
    
    // 3. 乐观锁更新票数（关键！防止超卖）
    char sql_update[512] = {0};
    snprintf(sql_update, sizeof(sql_update), 
        "UPDATE ticket_table "
        "SET tk_count = tk_count + 1 "
        "WHERE tk_id = %s "
        "AND tk_count < tk_max "    // 核心！只有没卖完才更新
        "AND status=1", 
        ticketid.c_str());
    
    if (mysql_query(conn, sql_update) != 0) {
        // 更新失败，回滚事务！
        mysql_query(conn, "ROLLBACK");
        return false;
    }
    
    // 4. 检查是否真的更新了（防止并发）
    if (mysql_affected_rows(conn) == 0) {
        // affected_rows == 0 说明WHERE条件没满足（卖完了）
        mysql_query(conn, "ROLLBACK");
        return false;
    }
    
    // 5. 插入预约记录
    char sql_insert[2048] = {0};
    snprintf(sql_insert, sizeof(sql_insert), 
        "INSERT INTO yd_table(yd_id, tel, tk_id, ctime, status) "
        "VALUES(0,'%s',%s,NOW(),1)", 
        escaped_tel, ticketid.c_str());
    
    if (mysql_query(conn, sql_insert) != 0) {
        // 插入失败，回滚事务！
        mysql_query(conn, "ROLLBACK");
        return false;
    }
    
    // 6. 提交事务（COMMIT）
    mysql_query(conn, "COMMIT");
    return true;
}
```

### 10.4 事务的ACID特性（面试必背）

| ACID                | 说明            | 本例中的体现               |
| ------------------- | ------------- | -------------------- |
| A (Atomicity) 原子性   | 要么全成功，要么全回滚   | 更新+插入要么都成功，要么都回滚     |
| C (Consistency) 一致性 | 数据从一个有效状态到另一个 | tk\_count不能超过tk\_max |
| I (Isolation) 隔离性   | 事务之间互不影响      | 用MySQL默认隔离级别实现       |
| D (Durability) 持久性  | 提交后数据持久化      | COMMIT后数据保存在磁盘       |

## 13. 核心扩展方案 - 完整实现

### 13.1 Redis缓存集成 - 完整代码

**创建文件：server/RedisCache.hpp**

```cpp
#ifndef REDIS_CACHE_HPP
#define REDIS_CACHE_HPP

#include <hiredis/hiredis.h>
#include <string>
#include <memory>

class RedisCache {
public:
    static RedisCache& getInstance() {
        static RedisCache instance;
        return instance;
    }
    
    bool init(const std::string& host = "127.0.0.1", int port = 6379) {
        ctx_ = redisConnect(host.c_str(), port);
        if (!ctx_ || ctx_->err) {
            if (ctx_) std::cerr << "Redis连接失败: " << ctx_->errstr << std::endl;
            return false;
        }
        return true;
    }
    
    // 1. 设置缓存（带过期时间）
    bool set(const std::string& key, const std::string& value, int expire_sec = 300) {
        redisReply* reply = (redisReply*)redisCommand(ctx_, 
            "SET %s %s EX %d", key.c_str(), value.c_str(), expire_sec);
        bool success = (reply && reply->type == REDIS_REPLY_STATUS && 
                       strcmp(reply->str, "OK") == 0);
        freeReplyObject(reply);
        return success;
    }
    
    // 2. 获取缓存
    bool get(const std::string& key, std::string& value) {
        redisReply* reply = (redisReply*)redisCommand(ctx_, "GET %s", key.c_str());
        if (!reply || reply->type != REDIS_REPLY_STRING) {
            freeReplyObject(reply);
            return false;
        }
        value = reply->str;
        freeReplyObject(reply);
        return true;
    }
    
    // 3. 分布式锁（防止超卖）
    bool lock(const std::string& key, int expire_ms = 10000) {
        redisReply* reply = (redisReply*)redisCommand(ctx_, 
            "SET %s 1 NX PX %d", key.c_str(), expire_ms);
        bool success = (reply && reply->type == REDIS_REPLY_STATUS && 
                       strcmp(reply->str, "OK") == 0);
        freeReplyObject(reply);
        return success;
    }
    
    // 4. 释放锁
    void unlock(const std::string& key) {
        redisCommand(ctx_, "DEL %s", key.c_str());
    }
    
private:
    RedisCache() : ctx_(nullptr) {}
    ~RedisCache() {
        if (ctx_) redisFree(ctx_);
    }
    
    redisContext* ctx_;
};

#endif // REDIS_CACHE_HPP
```

## 14. 大厂面试50问 - 逐题详解

### 基础篇（1-10）

**Q1: 为什么用Epoll，不用Select/Poll？**

面试官角度：想知道你对I/O多路复用的理解

标准答案：

```
Select有三个问题：
1. 单个进程能监听的FD数量有限制（一般1024）
2. 每次都要遍历整个FD集合，O(n)复杂度
3. 每次调用都要把FD集合从用户态拷贝到内核态

Poll解决了第1个问题（没有数量限制），但2、3还在

Epoll完美解决了三个问题：
1. 没有数量限制（只受内存）
2. O(1)复杂度，只返回就绪的FD
3. 用epoll_ctl()提前注册，不用每次拷贝
4. 支持ET（边缘触发），更高效

所以我们选了Epoll！
```

***

**Q2: EPOLLONESHOT的作用？**

面试官角度：想知道你对线程安全的理解

标准答案：

```
EPOLLONESHOT保证一个FD在同一时间只被一个线程处理！

场景：
没有EPOLLONESHOT时：
  Epoll线程检测到数据，通知Worker1
  Worker1处理中，FD又来数据
  Epoll又通知Worker2
  两个线程同时处理一个FD，数据乱了！

有EPOLLONESHOT时：
  FD触发一次后就不再触发
  Worker1处理完后显式重置EPOLLONESHOT
  下次数据才会再触发
```

***

**Q3: 为什么用线程池？直接新建线程不行吗？**

面试官角度：想知道你对性能和资源的理解

标准答案：

```
新建线程有三个问题：
1. 创建线程开销大（栈、TCB）
2. 线程太多上下文切换严重
3. 不可控（突发10万请求就建10万线程？系统崩溃！）

线程池的好处：
1. 核心线程常驻，不用反复创建销毁
2. 队列缓冲任务，削峰填谷
3. 线程数可控，不会超过最大限制

CachedThreadPool更灵活：
- 任务多时临时扩容
- 空闲时自动收缩（thread_wait_time_s）
```

***

**Q4: 为什么用连接池？**

面试官角度：想知道你对数据库性能的理解

标准答案：

```
每次新建连接有三个问题：
1. TCP三次握手
2. MySQL认证
3. 关闭连接TCP四次挥手
（一次连接要几十毫秒！）

连接池的好处：
1. 程序启动时预创建连接（init方法）
2. 业务线程从池子里拿，用完立即归还
3. 几乎零耗时

加上RAII的ConnectionGuard：
- 自动获取，自动归还
- 不用写try-finally，防止忘记归还！

本项目同时用了MySQL连接池和Redis连接池！
```

***

**Q5: 为什么引入Redis？**

面试官角度：想知道你对缓存架构的理解

标准答案：

```
Redis在本项目有四大作用：

1. 缓存热点数据
   票务信息（ticket:list）每次都被大量用户查询
   如果每次都查MySQL，数据库压力太大
   缓存到Redis后，QPS从100提升到500+

2. 分布式锁
   预约票务时，多个用户可能同时抢同一张票
   用Redis分布式锁保证同一时间只有一个线程能处理
   防止超卖问题

3. 缓存一致性
   采用"先更新数据库，再删缓存"策略
   保证数据准确性

4. 性能提升
   缓存命中率90%+，数据库压力降低80%
```

**Q6: Redis分布式锁怎么实现的？**

面试官角度：想知道你对分布式锁的理解

标准答案：

```
用SET NX PX命令实现：

SET lock:ticket:1 NX PX 5000

NX：只有key不存在时才设置（Not eXists）
PX：设置毫秒级过期时间（5000毫秒=5秒）

流程：
1. 尝试获取锁：SET lock:ticket:1 NX PX 5000
2. 如果返回OK，说明获取成功
3. 执行业务逻辑（预约）
4. 释放锁：DEL lock:ticket:1

为什么设置过期时间？
- 如果程序crash，锁没释放，其他线程永远拿不到锁
- 设置过期时间，即使crash，锁也会自动释放

潜在问题（面试加分）：
1. 锁误删：线程A的锁过期，线程B拿到锁，A执行完把B的锁删了
   解决：释放锁时检查value是否是自己设置的
   用Lua脚本保证原子性

2. Redis主从切换：Master还没同步给Slave就crash
   解决：RedLock算法，同时在多个Redis实例获取锁
```

**Q7: 缓存穿透/击穿/雪崩是什么？怎么解决？**

面试官角度：想知道你对缓存问题的理解

标准答案：

```
缓存穿透：
- 查询一个根本不存在的数据（如ticket_id=-1）
- 每次都穿透到数据库
- 解决：缓存空值、布隆过滤器、参数校验

缓存击穿：
- 某个热点key过期瞬间，大量请求同时查询
- 100个请求同时查MySQL，数据库压力爆炸
- 解决：分布式锁、永不过期、提前刷新

缓存雪崩：
- 大量缓存同时过期
- 解决：TTL随机、多级缓存、熔断降级、Redis高可用

本项目采用：
- 参数校验防止穿透
- 分布式锁防止击穿（可扩展）
- TTL随机防止雪崩（可扩展）
```

**Q8: 为什么用"先更新数据库，再删缓存"？**

面试官角度：想知道你对缓存一致性的理解

标准答案：

```
三种策略对比：

1. 先更新缓存，再更新数据库
   问题：缓存更新成功，数据库更新失败
   结果：缓存是新数据，数据库是旧数据 → 不一致！
   结论：❌ 不可用

2. 先删除缓存，再更新数据库
   问题：删除缓存后，更新数据库前，有请求来了
         请求查数据库（旧数据）→ 写入缓存
         数据库更新完成（新数据）
   结果：缓存是旧数据，数据库是新数据 → 不一致！
   结论：⚠️ 有问题，但可以用延迟双删解决

3. 先更新数据库，再删除缓存 ← 本项目采用
   分析：
   - 更新数据库成功，删除缓存失败：下次查询会加载新数据
   - 更新数据库失败：缓存不删，数据一致
   优点：最安全，不一致概率最低
   缺点：下次查询会穿透到数据库（但只有一次）
   结论：✅ 推荐
```

**Q9: Redis连接池和MySQL连接池有什么区别？**

面试官角度：想知道你对连接池设计的理解

标准答案：

```
相同点：
1. 都是单例模式
2. 都用list存储连接（LRU优化）
3. 都用条件变量等待
4. 都用RAII Guard自动归还

不同点：
1. 连接类型不同
   MySQL：MYSQL*连接上下文
   Redis：redisContext*连接上下文

2. 认证方式不同
   MySQL：用户名+密码+数据库
   Redis：可选密码（AUTH命令）

3. 超时设置不同
   MySQL：连接超时由MySQL服务器配置
   Redis：redisConnectWithTimeout设置2秒超时

4. 错误检查不同
   MySQL：mysql_ping()检查连接有效性
   Redis：redisContext的err字段（err==0表示正常）

设计思想相同，但细节适配各自客户端库！
```

**Q10: 为什么用事务？**

面试官角度：想知道你对数据一致性的理解

标准答案：

```
预约是两步操作：
1. 票数+1
2. 插入预约记录

不用事务的话：
  第1步成功，第2步失败
  票少了，但预约记录没生成
  数据乱了！

用事务的话：
  BEGIN → 第1步 → 第2步 → COMMIT
  任何一步失败 → ROLLBACK回滚

ACID特性：
- Atomicity原子性：要么全成功，要么全失败
- Consistency一致性：数据状态正确
- Isolation隔离性：事务之间互不干扰
- Durability持久性：提交后不丢失
```

#### 方案2：Redis+Kafka（推荐，性能高）

```

  用户 → Nginx（限流）→ 服务 → Redis预扣库存
  → Kafka异步处理 → 数据库

流程：
1. Redis预扣库存：INCR ticket:stock:1，>100返回失败
2. Kafka发送消息：tel,ticketid
3. 消费者组慢慢消费：真正执行数据库操作
4. WebSocket/轮询通知用户结果

优点：
- 性能最高（10万QPS没问题）
- 削峰填谷
- 数据库压力小

缺点：
- 引入Redis+Kafka，系统复杂
- 最终一致性（不是立即看到结果）
```

```
每个请求先拿Redis锁：
SET lock:ticket:1 NX PX 10000
拿到锁才执行预约
10秒后过期释放

优点：
- 简单，不容易出bug
- 并发可控

缺点：
- 锁粒度大，串行化，性能不如方案2
```
